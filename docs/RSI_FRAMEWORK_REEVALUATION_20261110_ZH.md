## 本项目的可验证闭环

1. 每个目标分别固定模型、注意力、计算硬件及互连、rank 分配、外部调度、工作负载和 evaluator 能力。训练、验证、测试分别承诺输入哈希。Agent、LongBench、chatbot、rollout 应以实际 token 序列、会话延续、分支/共享或到达事件体现差异。场景名称和 CPU fixture 不构成该场景在 GPU 上的验收。
2. 每轮使用同一个训练 archive 快照比较父代与子代。任务入口选择父代、训练证据和构造/变异/交叉算子。元入口选择训练证据和修订策略，自修订请求带入自己的完整源码。模型在同一响应返回 `source` 和 `plan`，受信层在评估前将方案与候选源码摘要关联。归档保存前后源码差异、操作选择、候选程序、评估记录、拒绝原因和晋级后下一轮实际调用的源码哈希。最后一轮晋级要等后续调用才能取得真实复用证据。
3. 独立冻结生成器对照从同一种子与资源上限开始，拥有同数的候选槽和一次计费的元调用槽，元调用产物丢弃。每轮分开记录预算上限、实际 provider token/call、裁判次数及耗时。错误调用与不可行候选留档。实际花费存在差异时按原始记录报告。近期 Terminal-Bench 研究也显示，搜索反馈与预算不匹配时容易把额外搜索误当成 harness 能力。 [匹配反馈/预算与留出设计](https://arxiv.org/abs/2607.12227) · [区分写出更新与未来实际受益](https://arxiv.org/abs/2605.30621)
4. 真实 GPU 晋级使用预登记区块。每个区块由受信裁判按固定协议启动和交错运行父代、子代、原生、固定生成器入围者及可选手写策略。每区块保留原始得分和正确性证据，要求所有配对方向一致，配对差值中位数超过预登记门槛。两层的结果分别报告。第一层比较生成器前后与固定生成器。第二层比较封存显存程序与原生及手写策略。封存后才执行测试，测试结果不回流生成或选优。

两入口控制器可以记录机械复用和评测归因。稳定收益仍依赖真实 GPU adapter 提供预登记实验、逐 rank KV 校验、外部调度与服务正确性证据，以及精确匹配的区块样本。专项 mock 测试只验证控制流、数据边界和配对门禁。
